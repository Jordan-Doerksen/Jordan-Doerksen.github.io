How the work runs

Work moves through four gates, around two loops, held by six rules, and every step leaves a record on disk.

I build trading instruments, training software and games, many at once. This page explains the method that keeps them apart and keeps them honest. It is written for a reader who has never heard the word loop. Nothing on it is clever. All of it is written down.

The outline below is empty. Each chapter fills in one part of it.

1. Three words

The words this page uses

Each one is a plain idea. The method is only these three, put in a fixed order.

Filed. The three words are on the diagram below.

  1. Word 1

    A gate

    A point where the work stops until someone says yes. The work cannot go around it. A gate has a name, a question, and a record of the answer.

  2. Word 2

    A loop

    A short list of steps that runs again and again. Each run ends with a check. If the check fails, the loop runs once more. If it passes, the work moves to the next gate.

  3. Word 3

    A rule

    A sentence that is always true, in every project, on every day. A rule is not a goal. If a rule is broken, the work is wrong, even when the result looks right.

The record: a three-word legend
  1. Gate

    Stops until someone says yes.

  2. Loop

    Runs again and ends with a check.

  3. Rule

    Always true.

2. The interview

The work starts with questions

The first command, /design-first:adopt, asks seven questions, one at a time. Each question marks the recommended answer. Silence is not approval. The command only asks. A script does every write.

Filed. The answers go into one file, DECISIONS.md.

  1. Question 1

    Root

    Which folder do your sessions start under? Root holds the entry `CLAUDE.md` and `.claude/settings.json`.

    Recommendedthe current working directory
  2. Question 2

    Brain

    Where should your brain live? It is your private folder for personal law, claims and state.

    Recommended`<root>/brain`
  3. Question 3

    Owner name

    What name should the guard use for you in its messages, and the brain's `me.md` carry as `owner.name`?

    Recommendedthe git `user.name` if one is set
  4. Question 4

    GitHub owner(s)

    Which GitHub owner(s) do your repositories push to? A remote that matches none of them is reported as FOREIGN by the Doctor.

    Recommendeda name you can see in the root's remotes, if any
  5. Question 5

    Brain as a git repo

    Should the brain be a git repository?

    RecommendedYes
  6. Question 6

    Frozen paths

    Any frozen paths: folders the guard must refuse to edit or delete, such as a reference copy you keep on purpose?

    RecommendedNone
  7. Question 7

    Settings scope

    The kit's deny/ask permission rules go in a settings file under root. Commit them or keep them personal?

    RecommendedCommit them in `.claude/settings.json`

3. Four gates

Where the work stops

Every project passes the four gates in this order. Each gate asks one thing, stops one thing, and leaves one record on disk. Read left to right. On a phone, read top to bottom.

Filed. Each gate left one record on disk.

  1. Gate 1

    The interview

    Before anything is built, I am asked what I want. One question at a time. Each question offers choices, the recommended one first, and each choice says what it gives and what it costs.

    Stops
    Building before the choice is mine.
    Leaves
    My answers, one per question.
  3. Gate 2

    The decisions manifest

    Every answer goes into one file, with the reason and the date. A part of the project is not coded until its decisions are in that file. Later, anyone can read why a thing is the way it is.

    Stops
    Code with no decision behind it.
    Leaves
    A file named DECISIONS, in the project.
  5. Gate 3

    The change request

    When a decision must change, it is not changed in place. A short note says what changes, why, what it touches, and how much can go wrong. I say yes or no. A yes updates the manifest and the log.

    Stops
    Drift: a change nobody agreed to.
    Leaves
    The request, the verdict, the log line.
  7. Gate 4

    The reviewer

    The work is checked by a reviewer that did not write it and cannot edit it. It reads the files, runs the checks, and gives one of three verdicts: pass, fail, or blocked. Only the reviewer can write the pass mark.

    Stops
    A builder grading its own work.
    Leaves
    The verdict, with the evidence beside it.

4. The build loop

What runs again and again

The gates are fixed points. Between them, a loop does the work. A project is built in chunks. A chunk is the smallest piece that works on its own. Each chunk goes around this loop once.

Filed. The loop repeats with every chunk.

  1. Step 1

    Build a chunk

    Only the files that belong to this chunk are touched. Nothing else is tidied, moved or improved on the way.

  3. Step 2

    Cross-check

    The chunk is held against three things: the manifest, the map of the project, and the one goal the project exists for. A chunk that drifts from any of them goes back to step 1.

  5. Step 3

    Report

    Four lines come back to me: where the work is, which files changed, what it needs from me, and what it is blocked on. Then the next chunk starts, or a change request does.

  7. Chunk 2

    The next chunk

    The next chunk goes around the same loop. It joins the parts the first chunk placed.

back to step 1 with the next chunk
The record: the loop on the spine
  1. The build loop

    Runs once per chunk. Each run ends with a check.

  3. Recording 3

    The guard

    A hook reads every tool call before it runs. A force push is refused. Staging a secrets file is refused. The refusal names the rule.

    $ git push --force origin main
GUARD: deny
  BLOCKED - that command destroys git history: --force rewrites published history.
  
  Git's recovery order is reflog, fsck --lost-found, stash, bundle; these commands remove exactly what that order depends on, on every branch. If this rewrite is genuinely wanted, Adopter runs it by hand.

$ git add .env
GUARD: deny
  BLOCKED - this command stages a file that looks like a credential: .env
  
  Secrets live in a gitignored .env, always; a token is never committed. If this one has leaked, rotate it first and assume it is already public. If this file is a deliberate exception, Adopter registers it in secretExceptions in the brain's doctor.config.json before it is staged; an exception is recorded, never assumed.

6. The control loop

Many projects, one head

I run many projects at once and I have one head. This loop keeps them apart. An idea goes in at the top. One line comes back at the bottom.

Filed. The report went back up to me.

  1. Top · one door, every idea

    Intake

    Every idea is written here first, in whatever shape it has. Intake sorts it into one of six domains, asks what is wanted and what is not, and hands one written request to that domain. It never does the work itself.

  3. Middle · six domains, one word each, one test each

    Six domains

    Each domain has one master. A master holds the domain's record, starts the work, and answers Intake with one line.

    • Desk It reads a market or serves the operator.
    • Games Someone plays it.
    • Site It ships under my own name.
    • Rail It teaches or checks a rule.
    • Tools It runs on this machine, for me alone.
    • Method It changes how the work is done, not what is built.
  5. Bottom · the writers

    A writer

    A master starts one writer per set of files. The writer gets a brief: the goal, the files, what done looks like, what is ruled out. It works on its own copy, touches nothing else, and reports back in four lines when its turn ends. Two writers never touch the same file.

  7. Back up

    The report

    The report goes back up: writer to master, master to Intake, Intake to me.

7. Six rules

What holds it together

None of these is about software. They are about not fooling myself. Where the public kit has a matching rule, its id and grade are shown. The grade says what stops you breaking the rule. The grades are the kit's own, read from its law file.

Filed. Each rule is on the diagram below.

  1. Rule 01

    One word, one test

    A domain is one noun for the thing built, never the method and never the tool. Each domain has one test. If an idea passes two tests, it is two ideas.

    No kit grade shown

  2. Rule 02

    One question at a time

    A question comes with choices. The recommended choice is first, and every choice says what it gives and what it costs. "Both are fine" is not an answer.

    Kit rule OWN-04 · HOOK

  3. Rule 03

    Nothing runs by itself

    No timers, no schedules, nothing at login. I start every job. If I did not press it, it did not happen.

    Kit rule SAFE-08 · not in the kit's public law

  4. Rule 04

    Blank beats wrong

    A panel with no data shows nothing. It never shows a guess. A check that could not look never reports green. Absent is not zero.

    Kit rule SAFE-04 · GATE

  5. Rule 05

    The record is on disk

    A conversation forgets. A file does not. Every decision, every verdict and every domain's state is a file I can open without opening the conversation.

    Kit rule AUTO-10 · BUILDABLE

  6. Rule 06

    A report is not proof

    "Done" is checked against the file, the test or the commit before it is believed. Proof is the command and what it printed. The checker is never the one who did the work.

    Kit rule AUTO-06 · ADVISE

8. Limits

What this does not do

Stated before the install, so that nothing here is a surprise. This chapter does not move.

  • One adopter per user profile: one pointer, at ~/.claude/design-first.json.
  • The guard inspects tool calls. It does not see nested shells, xargs, command substitution, git aliases or scripts that a session writes. The self-test asserts these gaps.
  • The Doctor's survey of repositories is informational unless surveyStrict is on in your brain config.
  • The Stop card asks once per turn that changed source. It grades no answer.
  • The kit never writes your user-level settings.json. When it wants a line there, it prints it.
9. Adopt

How to start

Three commands. The adopt command asks its questions, then a script writes the files and runs the Doctor. The remove command reverses exactly what adopt wrote and keeps anything you changed.

The specification, without the film

Generated from design-first 0.2.7, built 2026-10-20. The page lists 89 rules, each graded by what enforces it.

Every rule and what enforces it
  • HOOK 14
  • GATE 15
  • BUILDABLE 15
  • HONOUR 5
  • ADVISE 37
  • OWNER 3
  1. SAFE-01HOOKSecrets live in an ignored secrets file and never enter a commit; a leaked token is rotated first and removed second.
  2. SAFE-04GATEShow nothing rather than something false: a blank panel beats a wrong number, anything unverified is labelled, and absent is not zero.
  3. SAFE-06HOOKNever tidy, commit, reset or consolidate a dirty or untracked tree on your own initiative; some are dirty on purpose to protect something that works.
  4. SAFE-09HOOKA retired but load-bearing folder is never deleted, moved or archived while a live consumer still reads it.
  5. PRIN-01OWNERContext economy comes before every other rule: every decision about files, folders and config reduces what an agent must read before it can change something safely.
  6. PRIN-03GATEA fact about the disk is generated, never typed; if it can be derived, derive it.
  7. PRIN-04GATEThe next misbehaviour produces a mechanism, not a paragraph; writing the rule harder is the reflex that made adherence worse.
  8. PRIN-05GATEOne subject, one file; a rule stated in two places will disagree in two places.
  9. OWN-04HOOKAsk the owner one question at a time, as multiple choice, with the recommended option first; every option carries a reason to pick it, the recommendation says why it wins, no two options are offered as equally fine, and where the asking surface has no room for a reason the reason goes in the text above it.
  10. OWN-05ADVISEDo not ask the owner an implementation question they have no way to answer; when one answer is defensible, choose it, record why, and make it a config value so it stays reversible.
  11. OWN-06ADVISEDeliver what was asked, then stop; offer an addition in one line and do not build it first.
  12. OWN-07ADVISEWhen the project has a UI, anything the operator must run is a button in the app, not a script on the disk.
  13. OWN-10ADVISENever assume the best way: rank each decision low, medium or high and state the rank; a low one is acted on, a medium one gets a quick research pass first, a high one gets serious recon, and a case study supplements research but never replaces it.
  14. DES-01BUILDABLEInterview, then the decisions manifest, then the architecture map, then build in chunks, then cross-check; every project, no exceptions.
  15. DES-02ADVISEA subsystem is not coded until its foundational decisions are locked in the manifest; a later change is a Change Request, never drift.
  16. DES-03ADVISESplit by subject, never by size: a part leaves its file when it is independent and separately tunable, or when a real change finds a subject that falls out; a split-off file names what it uses, and a tiny helper stays inline.
  17. DES-04ADVISEEvery tunable value lives in a config file, never in logic; changing behaviour never requires changing code.
  18. DES-05ADVISEBuild the smallest slice that works, then show the owner; never over-engineer the slice and never skip the design.
  19. DES-06ADVISEDuring a chunk, edit only that chunk's files; no unrelated refactor.
  20. DES-07ADVISEDocuments are co-equal artifacts, updated before the work is called done; document debt is technical debt.
  21. DES-08ADVISEEvery workaround carries an inline note saying what failed and why this is the fix, because an unexplained correction gets cleaned up and the defect returns.
