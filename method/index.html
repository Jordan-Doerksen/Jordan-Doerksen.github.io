How the work runs

Gates, loops
and rules.

I build trading instruments, training software and games, many at once. This page explains the method that keeps them apart and keeps them honest. It is written for a reader who has never heard the word loop. Nothing on it is clever. All of it is written down.

1. Three words

The words this page uses

Each one is a plain idea. The method is only these three, put in a fixed order.

A gate
A point where the work stops until someone says yes. The work cannot go around it. A gate has a name, a question, and a record of the answer.
A loop
A short list of steps that runs again and again. Each run ends with a check. If the check fails, the loop runs once more. If it passes, the work moves to the next gate.
A rule
A sentence that is always true, in every project, on every day. A rule is not a goal. If a rule is broken, the work is wrong, even when the result looks right.
2. Four gates

Where the work stops

Every project passes the four gates in this order. Each gate asks one thing, stops one thing, and leaves one record on disk. Read left to right. On a phone, read top to bottom.

  1. Gate 1

    The interview

    Before anything is built, I am asked what I want. One question at a time. Each question offers choices, the recommended one first, and each choice says what it gives and what it costs.

    Stops
    Building before the choice is mine.
    Leaves
    My answers, one per question.
  3. Gate 2

    The decisions manifest

    Every answer goes into one file, with the reason and the date. A part of the project is not coded until its decisions are in that file. Later, anyone can read why a thing is the way it is.

    Stops
    Code with no decision behind it.
    Leaves
    A file named DECISIONS, in the project.
  5. Gate 3

    The change request

    When a decision must change, it is not changed in place. A short note says what changes, why, what it touches, and how much can go wrong. I say yes or no. A yes updates the manifest and the log.

    Stops
    Drift: a change nobody agreed to.
    Leaves
    The request, the verdict, the log line.
  7. Gate 4

    The reviewer

    The work is checked by a reviewer that did not write it and cannot edit it. It reads the files, runs the checks, and gives one of three verdicts: pass, fail, or blocked. Only the reviewer can write the pass mark.

    Stops
    A builder grading its own work.
    Leaves
    The verdict, with the evidence beside it.
3. Two loops

What runs again and again

The gates are fixed points. Between them, two loops do the work. The first builds a project in pieces. The second keeps many projects apart.

The build loop

A project is built in chunks. A chunk is the smallest piece that works on its own. Each chunk goes around this loop once.

  1. Step 1

    Build a chunk

    Only the files that belong to this chunk are touched. Nothing else is tidied, moved or improved on the way.

  3. Step 2

    Cross-check

    The chunk is held against three things: the manifest, the map of the project, and the one goal the project exists for. A chunk that drifts from any of them goes back to step 1.

  5. Step 3

    Report

    Four lines come back to me: where the work is, which files changed, what it needs from me, and what it is blocked on. Then the next chunk starts, or a change request does.

back to step 1 with the next chunk

The control loop

I run many projects at once and I have one head. This loop keeps them apart. An idea goes in at the top. One line comes back at the bottom.

Topone door, every idea

Intake

Every idea is written here first, in whatever shape it has. Intake sorts it into one of six domains, asks what is wanted and what is not, and hands one written request to that domain. It never does the work itself.

Middlesix domains, one word each, one test each

  • Desk

    It reads a market or serves the operator.

  • Games

    Someone plays it.

  • Site

    It ships under my own name.

  • Rail

    It teaches or checks a rule.

  • Tools

    It runs on this machine, for me alone.

  • Method

    It changes how the work is done, not what is built.

Each domain has one master. A master holds the domain's record, starts the work, and answers Intake with one line.

Bottomthe writers

A writer

A master starts one writer per set of files. The writer gets a brief: the goal, the files, what done looks like, what is ruled out. It works on its own copy, touches nothing else, and reports back in four lines when its turn ends. Two writers never touch the same file.

the report goes back up: writer to master, master to Intake, Intake to me
4. Six rules

What holds it together

None of these is about software. They are about not fooling myself.

  1. 01

    One word, one test

    A domain is one noun for the thing built, never the method and never the tool. Each domain has one test. If an idea passes two tests, it is two ideas.

  2. 02

    One question at a time

    A question comes with choices. The recommended choice is first, and every choice says what it gives and what it costs. "Both are fine" is not an answer.

  3. 03

    Nothing runs by itself

    No timers, no schedules, nothing at login. I start every job. If I did not press it, it did not happen.

  4. 04

    Blank beats wrong

    A panel with no data shows nothing. It never shows a guess. A check that could not look never reports green. Absent is not zero.

  5. 05

    The record is on disk

    A conversation forgets. A file does not. Every decision, every verdict and every domain's state is a file I can open without opening the conversation.

  6. 06

    A report is not proof

    "Done" is checked against the file, the test or the commit before it is believed. Proof is the command and what it printed. The checker is never the one who did the work.

The masters and the writers are AI sessions. The shape does not depend on that. It would hold with people, and it was drawn so that it would.
